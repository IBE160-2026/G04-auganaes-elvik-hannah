- (decision) Purpose/audience: spine is primarily a build substrate for the 3-person team (Eirik, Steffen, Hannah, all working together live today) to implement the app from; secondary need is to be able to show/explain the team's process and decisions as part of the IBE160 course deliverable. No separate polished artifact requested yet; revisit at Finalize step 5.
- (decision) Backend framework: FastAPI (chosen over Django+DRF and Flask). Binds: all API routes, auth/permission middleware, and request/response validation to FastAPI + Pydantic conventions. Prevents: mixing WSGI (Django/Flask) sync patterns with the AI-assistant's async LLM calls.
- (version) FastAPI 0.141.x current stable (web-verified, Oct 2026). React 19.2 current stable; create-react-app officially deprecated (2025-02-14) in favor of Vite. Decision: Vite + React (SPA), not Next.js/Remix, since backend is a separate FastAPI service, not a Next.js API.
- (decision) Hosting: Supabase (Postgres DB + file storage, free tier: 500MB DB/1GB storage, pauses after 7 days DB inactivity, restorable) for data + Photo Evidence storage; Render free web service for FastAPI backend; Vercel for the Vite/React static frontend. All three provide HTTPS by default, required for Web Push. Binds: deployment target and photo-storage mechanism. Prevents: local-disk photo storage assumptions that wouldn't survive Render's ephemeral filesystem.
- (decision) Data layer: SQLModel (unified Pydantic+SQLAlchemy models) over separate SQLAlchemy 2.0 + Pydantic schemas. Binds: every entity (Home, Member, Task, TaskInstance, PhotoEvidence...) is defined once. Prevents: API schema and DB model drifting apart across 3 developers. Known caveat (web-verified): SQLModel currently pins to SQLAlchemy ~1.4.41 internally, not full 2.0 — acceptable for this project's scale.
- (decision) Auth: short-lived JWT access token kept in React memory (never localStorage) + long-lived refresh token in an httpOnly, Secure, SameSite=None cookie, since frontend (Vercel) and backend (Render) are cross-origin. Binds: every protected FastAPI route reads the Role off the verified JWT claims, not a client-supplied field. Prevents: two routes independently trusting a client-sent role/user-id instead of the token.
- (decision) AI provider: Google Gemini Flash-Lite (free tier, no credit card, ~1000 req/day, web-verified Oct 2026) for both the FR-14 quick-answer and FR-15 chat escalation. Binds: all AI-assistant calls go through one backend service wrapping the Gemini API (never called directly from React, to keep the API key server-side and keep the disclaimer-injection logic in one place). Prevents: a free-tier rate-limit surprise from calling Gemini directly from the client, and the disclaimer text drifting between the quick-answer and chat code paths.
- (decision) Notifications: Web Push (VAPID) via pywebpush on the FastAPI backend, service worker on the React/Vite frontend. The app is a PWA (manifest.json + service worker + install-prompt UX) specifically so iOS Safari push works (web-verified: iOS 16.4+ only supports Web Push for a Home-Screen-installed PWA, not an ordinary browser tab). Binds: notification delivery path and the frontend's install-prompt requirement. Prevents: iPhone users silently getting zero notifications, which would break the FR-10/Cross-Cutting 'absence of notification means nothing due' reliability guarantee.
- (decision) Frontend language: TypeScript (not plain JS). Binds: types are generated from FastAPI's OpenAPI schema (e.g. openapi-typescript) rather than hand-written, so frontend and backend data shapes can't silently diverge. Prevents: 3 developers independently assuming different shapes for the same API response.
- (decision) Frontend data layer: TanStack Query for all server-state fetching/caching/revalidation (task lists, notifications, portfolio dashboard). Binds: components read server data only through Query hooks, never ad-hoc fetch+useState. Prevents: inconsistent caching/staleness behavior across components built by different team members.
- (decision) Permission enforcement pattern: a single FastAPI dependency (e.g. require_role(...)) reads the Role from the verified JWT and is attached to every protected route; no route hand-rolls its own role check. Binds: FR-3/FR-5/FR-8/FR-13's server-side enforcement NFR to one implementation path. Prevents: two routes enforcing the same Role rule with subtly different logic.
- (decision) Task-completion state mutation: one domain-layer function (e.g. complete_task_instance()) is the only path that marks a Task instance complete and triggers FR-9's reschedule-from-completion-date. Both the plain self-checkoff endpoint (FR-17) and the photo-evidence-upload auto-approve path (FR-19) call through it rather than duplicating the completion/reschedule logic. Prevents: the two completion paths (checkbox vs photo upload) rescheduling or attributing completion differently.
- (decision) Repo structure: single monorepo (existing group GitHub repo) with /frontend (Vite+React+TS) and /backend (FastAPI) top-level folders, not separate repos. Seed decision, low ambiguity given the team already shares one repo.
- (decision) Photo Evidence storage key: each task's required photo is stored under a deterministic server-controlled key (e.g. tasks/{task_id}/evidence.jpg) in Supabase Storage. Uploading a new photo for the same task overwrites that key server-side. Binds: FR-19's auto-replace/no-accumulating-history rule to the storage layer itself. Prevents: replacement depending on the client remembering to delete the old photo first.
- (decision) Real-time sync: none needed. FR-7's 'Mari sees Peter already did it' only requires freshness when a screen is opened/focused, not live push while already open — TanStack Query's refetch-on-mount/window-focus covers this. No WebSocket/SSE layer. Prevents: over-building realtime infrastructure the UJs don't actually require.
- (decision) Environments: single shared environment (one Supabase project, one Render service, one Vercel deployment) used for both development and the course demo/submission — no separate staging, given 3-person/13-week academic scope. Risk accepted and logged rather than silently assumed: all three developers share one dev database.
- (decision) Background job trigger: a free external cron pinger (cron-job.org) hits a dedicated FastAPI endpoint (e.g. POST /internal/run-due-check) every 10-14 minutes. This both keeps the free Render service awake (avoids its 15-min spin-down, web-verified) and triggers the due/overdue-task scan that fires FR-10 push notifications and FR-11 fairness-targeted reminders. Render itself calls this workaround unsupported/not guaranteed reliable. Fallback (confirmed reversible, no re-architecture needed): upgrade to Render's paid tier (~/mo) for guaranteed always-on if the free cron-ping proves unreliable in practice — same codebase, same deployment target, just drop the workaround.
- (question) PRD OQ-2 (notification delivery window) is now bounded by this architecture: checks run on the cron-ping's cadence (~10-14 min), so 'immediate' delivery isn't possible without the paid tier running a tighter interval. Team should treat 'due/overdue, checked every ~10-15 min' as the v1 answer to OQ-2 unless they upgrade.
- (decision) Data model core shape: Role lives on the Membership (User x Home join entity), not on the User account itself. Binds: User can hold different Roles in different Homes simultaneously (one Membership row per Home, each with its own Role). Prevents: a model where Role sits on User, which would hard-block multi-Home dual-role support. Side effect: resolves PRD Open Question 3 (dual-role-across-Homes) for free — feed this back to the PRD as a closed OQ.
- (decision) FR-11 fairness threshold resolved (closes PRD OQ-4): a targeted nudge fires when a Member has 0 completions out of the last 3 instances of a given recurring shared task, while at least one other Member completed at least one of those 3. Binds: the due-check background job's fairness-nudge logic to this exact rule. Feed back to PRD OQ-4 as closed.
- (decision) Photo Evidence eligibility (resolves the PRD's Privacy Constraints [ASSUMPTION]): Task types carry a system-controlled photo_evidence_eligible flag, seeded by the team (not Landlord-editable). The FR-18 require-photo-evidence endpoint rejects the request server-side if the Task's type isn't flagged eligible. Binds: eligibility enforcement to the data layer, not the UI. Prevents: a direct API call letting a Landlord require photo evidence on a privacy-sensitive task type.
