# PRD ↔ UX Spine Reconciliation

Comparing `prd.md` against `DESIGN.md` + `EXPERIENCE.md`. Each gap lists a one-line description and the PRD location it traces to.

## Missing IA / behavioral decisions (PRD content not reflected in the spines)

1. **No surface for Household Members to adjust Must/Should or Frequency.** FR-5 and FR-8 grant this editing right to *both* Household Members and Landlords, but the IA table's only admin surface is "Landlord Home Admin" (Landlord-only). There's no equivalent surface, or Task Detail edit affordance, described for a Household Member to change a classification or frequency. A developer has no page to build this into. — PRD FR-5, FR-8; EXPERIENCE.md IA table.
2. **No surface for adding/creating tasks, or reviewing the app's initial recommended task set.** FR-4 has the app "suggest" a classification "for each task," and UJ-2 explicitly has Johan "review the app's suggested Must tasks for the new Home and adjust a few" during Home setup — but no IA row, component, or flow step covers where tasks originate, how the initial recommended list is presented, or whether users can add a custom task at all. — PRD FR-4, FR-1 ("supports full configuration... with zero Tenants present"), UJ-2; EXPERIENCE.md IA table & Key Flows.
3. **No Home-switcher / multi-Home navigation for non-Landlord users.** The Landlord gets a Portfolio Dashboard, but nothing addresses how a Household Member or Tenant who belongs to more than one Home (not ruled out by the PRD) moves between Homes, or what their landing surface is when they have >1. Settings/Profile doesn't mention it either. — PRD §2 Glossary (Home, Member), FR-1; EXPERIENCE.md IA table.
4. **No surface for the Tenant to receive/read the AI-generated onboarding guide.** FR-16 requires the guide be generated and accessible to a new Tenant; EXPERIENCE.md's UJ-2 flow only covers the Landlord's side ("queued to send once a Tenant accepts") — no IA row or flow step shows the Tenant actually opening/reading it. — PRD FR-16; EXPERIENCE.md IA table, UJ-2 flow.
5. **No Member-removal or leave-Home action.** Members & Invite lists "view member list" and invite generation only; nothing addresses removing a Tenant/Household Member or a user leaving a Home. Not strictly required by an FR, but worth a deliberate scope note rather than silent omission, since Home membership is core to the product. — PRD §4.1; EXPERIENCE.md IA table.
6. **Broadcast message history not addressed.** FR-12 covers sending a broadcast; neither doc says whether a Tenant can see past broadcast messages anywhere after the push notification is dismissed, or whether the Landlord can see a sent-message log. — PRD FR-12; EXPERIENCE.md Component Patterns (Broadcast composer).

## PRD Open Questions / Assumptions the spines have already resolved confidently

7. **Photo Evidence eligibility enforcement is undecided in the PRD but the UX commits to an unconstrained per-task toggle.** The PRD's own Privacy Constraints section flags `[ASSUMPTION: enforcement mechanism (curated allowlist vs. Landlord judgment) not yet decided — deferred to architecture]`. DESIGN.md's "Photo evidence upload control" and EXPERIENCE.md's Component Patterns describe it simply as rendering "only when FR-18 applies to this task," with no UI concept for restricting *which* task types a Landlord is even allowed to flag — silently assuming Landlord judgment with no system check, one of the two undecided options. — PRD Privacy Constraints (Assumption); DESIGN.md "Photo evidence upload control"; EXPERIENCE.md Component Patterns row "Photo evidence upload."
8. **Scope-cut Open Question 1 (FR-11, FR-16, FR-18/19, FR-20 flagged as possible deferrals) is not reflected as contingent anywhere in the UX spine.** EXPERIENCE.md builds full IA rows and flows for the Portfolio Dashboard, fairness-based targeting, Photo Evidence, and the onboarding guide with no fallback/graceful-degradation notes, even though the PRD explicitly says these may need to be cut and gives a cut order. If the scope call goes the PRD's way, the UX spine has no documented "what ships without X" fallback. — PRD §8 Open Question 1; EXPERIENCE.md IA table & Key Flows (UJ-2, UJ-3).
9. **Dual-role users (Open Question 3) are neither resolved nor flagged.** The PRD leaves open whether one user account can be a Landlord in one Home and a Household Member in another. The UX spine's "Create Home" IA row lists both roles as options without addressing whether/how a single account crosses roles, and Settings/Profile has no per-account role or multi-Home concept — the ambiguity is inherited silently rather than called out for Architecture to resolve before build. — PRD §8 Open Question 3; EXPERIENCE.md IA table.
10. **FR-11 fairness threshold (Open Question 4) is undefined in the PRD, yet UJ-3's flow depicts the mechanic as already working ("targeted only to him... others already completed this recurring task") with confident, specific behavior.** This is backend logic more than UI, but the UX flow's specificity implies a resolved threshold rule that doesn't yet exist. — PRD §8 Open Question 4; EXPERIENCE.md Key Flows UJ-3, step 1.
11. **FR-10 delivery-window timing (Open Question 2) is unresolved, but the UX spine has already committed to "no in-app notification inbox in v1"** as the sole fallback design decision, without noting this choice is contingent on push being reliable/timely — if the delivery window ends up coarse (e.g., daily batch), the lack of an inbox becomes a bigger product risk than the current confident, unqualified framing suggests. — PRD §8 Open Question 2; Cross-Cutting NFRs (Notification reliability); EXPERIENCE.md Information Architecture note ("No in-app notification inbox in v1").

## Minor / lower-priority

12. **Glossary term "Completion" (trust-based, no undo mentioned) has no corresponding "undo/uncheck a completed task" state** in EXPERIENCE.md's State Patterns, though this is arguably out of PRD scope too and not a hard requirement — flagged only because self-checkoff mistakes seem plausible in daily use.
13. **NFR "Notification reliability"** (missed notification undermines core value prop) has no corresponding UX mitigation beyond the "No push permission granted" state — no design response for the case where permission *is* granted but delivery is merely slow/unreliable (a platform/OS-level risk the PRD's own NFR calls out as core to product trust).
