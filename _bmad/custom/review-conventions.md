# Project conventions for code reviewers (Husly, IBE160 G04)

These are deliberate conventions of this project. Do not report their absence from the diff under review as a finding. Report a finding only if the diff itself contradicts one of them.

Source: Epic 1 retrospective (`_bmad-output/implementation-artifacts/epic-1-retro-2026-11-08.md`, finding P5, action 7). In all seven Epic 1 stories, reviewers filed these as findings and each was triaged as false.

- **KI-logg session files** (`docs/ki-logg/okter/*.md`) are exported by a Stop hook and committed together with the work at the end of a session. The diff under review excludes them on purpose.
- **`docs/ki-logg/korrigeringer.md`** is updated after the code review, when the change is presented, with the corrections the reviews found. It is never part of the diff the reviewers see.
- **`_bmad-output/implementation-artifacts/sprint-status.yaml`** moves a story to `in-progress` in the spec's baseline commit, to `review` when the PR opens, and to `done` in a separate status commit on `main` after merge. It is often unchanged in the reviewed diff.
- **Generated files** (`frontend/openapi.json`, `frontend/src/api/schema.d.ts`) are regenerated by `uv run python -m app.export_openapi` and `npm run gen:api`, and checked by `tests/test_openapi_sync.py` and a CI diff step. They may be excluded from the diff.
- **The spec's own Review Triage Log and Spec Change Log** are filled in by the orchestrator during and after review.
- **Session logs** (`.logs/<user>/`) are committed separately with the message `Logg: <title>`.
- **README and `.env.example`** are updated in the same PR as the change that needs it (CLAUDE.md). If the diff changes how to run the app and README is unchanged, that *is* a finding.
